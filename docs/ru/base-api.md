# Базовый API сессии

Канонический источник: [English](../en/base-api.md).

`api.base.v1` определяет тела запросов и ответов команд сессии. Здесь нет
сервиса, маршрутов, HTTP-методов, WebSocket framing, request ID, статуса ответа
или сообщения ошибки. Их определяет транспорт отдельно. HTTP-аннотации
[GameService](game-service.md) не назначают этим сообщениям endpoints.

## Команды и тела сообщений

| `CommandType` | Номер | Запрос → ответ | Назначение |
| --- | --- | --- | --- |
| `COMMAND_TYPE_UNKNOWN_UNSPECIFIED` | 0 | — | Неуказанная команда |
| `sync` | 1 | `SyncRequest` → `SyncResponse` | Обновление пользователя и оффера |
| `login` | 2 | `LoginRequest` → `LoginResponse` | Аутентификация и данные подписи |
| `start` | 3 | `StartRequest` → `StartResponse` | Получение контекста и настроек |
| `play` | 4 | `PlayRequest` → `PlayResponse` | Выполнение действия |
| `ready` | 5 | Отдельной пары сообщений нет | Только значение enum |
| `gift_mode` | 6 | `GiftModeRequest` → `GiftModeResponse` | Выбор режима гифтов/баланса |

Схема не проверяет значение команды внутри конкретного запроса. Из значения
enum нельзя выводить наличие `ReadyRequest`, DTO ошибки или успешного поведения
сервера. Номера полей и точные типы приведены в
[справочнике схем](schema-reference.md).

## Login и start

`LoginRequest` содержит `command`, `game_name`, `token` и `language`.
`LoginResponse` содержит `user`, `sign_key` и `gift_spin`. В ответе нет
`session_id`: способ получения session ID принадлежит транспортной интеграции.
Данные подписи должны оставаться приватными; схема не определяет алгоритм подписи.

`StartRequest` содержит `command`, `game_name`, `session_id`, `sign_key` и
optional-строку `mode`. `StartResponse` содержит `user`, `context` и `settings`.
Схема не ограничивает `mode` значениями enum и не устанавливает переключение
финансирования гифтов через это поле. Явный выбор описан в
[gift mode](gift-mode.md).

Обычная последовательность приложения: login, start, затем разрешённые
контекстом действия; сама схема не содержит state machine и обязательного
порядка запросов. Восстанавливайте сессию по подтверждённому контексту, а не
выводите запуск нового раунда из наличия бонуса или промо-оффера.

## Play и действия

`PlayRequest` содержит `command`, `action`, `session_id`, `sign_key`, boolean
`gift_spin`, boolean `quick_spin` и `int32` `set_denominator`.
`PlayResponse` содержит `user` и `context`.

`Action` содержит строку `name` и сообщение `ActionParams`. Все шесть
параметров имеют явное presence:

| Параметр | Тип | Назначение |
| --- | --- | --- |
| `bet_per_line` | optional int32 | Ставка на линию |
| `lines` | optional int32 | Число выбранных линий |
| `feature_id` | optional int32 | Выбор фичи по контракту игры |
| `user_choose` | optional int32 | Выбор при покупке по контракту игры |
| `ante_bet` | optional string | Выбор ante в формате интеграции |
| `cheat` | optional string | Отладочная инструкция интеграции |

Пакет не перечисляет названия действий и ID фич. Имена доступных следующих
действий находятся в `Context.actions`; значения и авторизация принадлежат
игре/backend. `gift_spin` описывает запрошенный раунд, а `paused`
подтверждённого оффера — выбранный режим. Ни одно из этих полей не доказывает,
как сервер профинансировал принятый раунд. Пакет не списывает баланс, не
выполняет settlement и повторы. В частности, повторная отправка `play` не имеет
гарантии идемпотентности со стороны пакета.

Пример тела в protobuf JSON с proto-именами:

```json
{
  "command": "play",
  "session_id": "example-session",
  "sign_key": "example-sign",
  "action": { "name": "spin", "params": { "bet_per_line": 10, "lines": 20 } }
}
```

Пропущенные неявные boolean декодируются как `false`; пропущенный
`set_denominator` — как ноль. Их смысл для backend нужно проверять в интеграции.
Условное тело запроса не подтверждает допустимость ставки.

## Sync и применение ответа

`SyncRequest` содержит `command`, `session_id` и `sign_key`.
`SyncResponse` содержит `user` и корневой `gift_spin`. Полного `context` или
`settings` в нём нет, поэтому он не взаимозаменяем со `StartResponse`.

Оффер расположен в корне ответов login/sync/gift-mode и внутри `context` в
start/play. Используйте схему фактической группы ответа. Применяйте
подтверждённые сервером суммы и состояние по правилам корреляции запросов и
жизненного цикла приложения. Сам парсинг не проверяет актуальность, успешность,
полноту ответа и его связь с нужным запросом. Коды ошибок, истечение сессии и
восстановление этими сообщениями не определены.
